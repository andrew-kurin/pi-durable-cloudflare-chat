# Pi 1.3.0 compatibility migration (#55)

Prepared from verified main `13a6633fcea67f7ac7da948174aa9a4393a36617` (PR56). This is a source migration and offline validation; no production data, Cloudflare deployment, Spark host, credentials, or paid inference were accessed.

## Scope and compatibility decisions

- Exact direct pins: `@earendil-works/pi-durable`, `pi-ai`, and `chord` **1.3.0**. Lockfile also resolves telemetry and codemode at 1.3.0, Photon at 0.3.3, QuickJS WASI at 3.6.2. `npm ls` shows one Pi/Chord instance; Agents remains **0.28.0**, with its compatible `^1.0.0` Pi peers. Package manifests require Node >=22.19.0; CI uses Node 24.
- Re-reviewed `dist/utils/retry.js`, `dist/harness/generation.js`, and `dist/harness/compaction.js`. The existing patch anchors match stable 1.3.0. Both patches remain exact-version/source guarded and idempotent. Status-first terminal HTTP classification remains before textual fallback; upstream's added gateway/network patterns remain intact. Both runner dispatch boundaries retain persisted task/conversation identity, including compaction's kind header.
- Change tool execution `content` to `output`, including search-check readers and offline eval/test tools. Do **not** rewrite saved/model-message `content`. Legacy five-minute read caches and write-once `read-result` memos normalize on reads without replacing the original memo or spending another read reservation. Pi itself migrates active `pi.tool` v1 tasks to v2 tagged model inputs/results. No app code assumes every saved receipt has a new tag.
- The private OAuth dist import is still present at the same path and bundles in workerd; fake device/refresh tests pass. It remains an explicitly pinned adapter requiring review on future upgrades.
- Chord imports remain its context/delta APIs. The HTTP/SSE protocol is unchanged. No codemode, images, nested-tool execution, Chord RPC, or unreleased upstream main features are enabled. Nested tool events are explicitly excluded from transcript rows rather than publishing their program results.
- The runner still uses `openaiProvider()`'s model catalog. Offline inspection of all three runner models (Sol 6.1, Sol 6, Luna 6) reports **272,000** context tokens and 128,000 maximum output tokens. The production policy stays 16,384 reserved / 32,768 recent / 32,768 background: estimated background 222,848, blocking 255,616. No 500K window is inferred. SIWC still omits output-limit tuning; these are not billing/output guarantees.

## Session and history failure behavior

Pi 1.3 closes a Session after a fatal storage error. Pending submission waits reject; event watches terminate as `session_failed`. A read-only invalid `StorageRequestError` fails its read without closing the Session; the same exception from `Storage.commit` is fatal.

Agents 0.28 caches the opened Harness even after that failure. `HarnessRecovery` observes full closure, then serializes disposal of that cache at the next authenticated request boundary. The next adapter access opens a new SQLite storage/Harness over committed data. The request that failed is not automatically retried. A commit may have taken effect before its error, and unsafe external actions may already have run; reconcile saved receipts/workspace status first. Repeated storage failures remain errors, not retry loops. This HTTP recovery path does not promise that a background alarm alone repairs the adapter before another request.

History sends a final safe storage-unavailable projection, releases its stream lease, and closes. Compaction failure is projected as a safe status, including snapshot/reconnect state, without copying its raw error. A successful summary clears it; an aborted/no-op compaction does not clear an earlier failure. Full-history pagination, the snapshot tail, fork traversal, masking, and thinking exclusion remain intact.

## Disposable migration and rollback rehearsal

`tests/fixtures/pi-1.1-storage.json` is a synthetic SQLite image generated by the actual **1.1.0** Harness. Its generator is retained in `tests/fixtures/generate-pi-1.1.mjs` and refuses another package version. Run it from an isolated 1.1.0 dependency tree (copy it under that tree's `tests/fixtures/`); it never uses the network. It captures commits before graceful shutdown, including:

- Unsafe `workspace_exec` at persisted execute intent; one previously dispatched operation in a separate synthetic journal table.
- A sequential queued tool call, a separate genuinely pending v1 tool task, and a queued follow-up submission.
- A running safe `github_read` with the old `{content: ...}` memo.
- Original entries/entry metadata, conversation ownership/model settings, and request-ID receipts.

`tests/pi-migration.test.ts` restores this into a fresh local SQLite file and opens it with 1.3.0. It verifies all three old tool tasks become v2 with tagged input/results, old unsafe intent does not dispatch again, the queued call runs once, the safe read returns its legacy memo without HTTP, and all original entries and receipt IDs survive. Another close/reopen preserves request deduplication. Cache normalization is separately exercised without HTTP or quota reservation.

The opt-in `tests/pi-rollback-rehearsal.mjs` uses a **separate** legacy installation; it never inserts legacy dependencies into the app's lockfile. CI runs it after the full suite. To reproduce locally:

```sh
task_pi_legacy=$(mktemp -d)
npm install --prefix "$task_pi_legacy" --ignore-scripts --no-audit --no-fund --save-exact @earendil-works/pi-durable@1.1.0 @earendil-works/pi-ai@1.1.0 @earendil-works/chord@1.1.0 @earendil-works/pi-telemetry@1.1.0
node tests/pi-rollback-rehearsal.mjs "$task_pi_legacy"
rm -rf "$task_pi_legacy"
```

The rehearsal captures a new crash image after 1.3 migrates active tools. Actual 1.1.0 inspection reports three `task_too_old` blocked tasks. Reopening the original snapshot with 1.1.0 instead retains history, deduplicates the old operation receipt, and keeps the pre-upgrade external-operation marker. Thus **code-only rollback is not a safe recovery plan**, even though stable 1.3.0 still uses SQLite schema version 1. Unreleased main's schema-v2 migration is outside this work.

The approved release uses the forward-only maintenance procedure in [DEPLOY.md](../DEPLOY.md#forward-only-pi-maintenance-window). Pause admission and background recovery before the first 1.3 persistent open; drain old-runtime work, confirm every workspace is closed/stopped, and capture native bookmarks before migration. Keep all current DO/application state, runner journals, workspace journals, IDs and reservations in place. Validate idle saved history on 1.3 while admission remains paused; explicitly resume only the reviewed checkpoint/revision/serving version. If validation fails, stay paused and repair forward with 1.3. This path does not need coordinated snapshot restoration because it never rewinds state. A bookmark is a bounded inspection checkpoint, not proof of a cross-system recovery capability. If restore is ever separately proposed, it loses later writes and can revive pending intent: reconcile operations and retain every post-snapshot dispatch fence before permitting execution. Never restore an old runner journal alongside chat data and assume at-most-once behavior. This rehearsal validates local file storage and the incompatibility/restore boundary, **not** a Cloudflare production backup/restore procedure or restoration of real workspace files. No automated production restore tool is included.

## Integration and release gates

Keep this compatibility PR separate from #50, #53, and #54. Re-run all checks against their eventual combined commits. In particular, #54's bounded SSE queue must retain `session_failed` safe-frame/lease cleanup from `HistoryFeed`; slow/disconnected-reader capacity and expiry are tested separately here, but this migration does not fix that backpressure issue. #53's export behavior and #50's transport test cleanup remain independent.

The four-PR integration was reviewed and approved for rollout on 2026-10-20. The additional maintenance window was explicitly approved before implementation. Release requires fresh exact-head CI, the forward-only gate above, native checkpoint capture in production and bounded owner/history/Access verification. Live provider/compaction quality checks remain outside this window; no paid inference is required to validate retained idle history. A future restore or access expansion still needs separate approval.
