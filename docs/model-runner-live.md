# SIWC backend and authenticated runner: implementation, not activation

Draft PR36 adds an explicit Worker provider, SIWC service, protected credential
owner and separate live entrypoint. Production routing and credentials are
unchanged. The approved fake server/deployment remains `offline-fake-only` and
never imports the live entrypoint. No new credentials, endpoint or service were
configured; no live inference or refresh was performed during this implementation.

## Contract

`createSiwcRunnerProvider` takes explicit HTTPS `/v1/responses`, injected fetch,
a non-extractable HMAC key and **one already-durable model-round ID**. Construct a
new provider for each model round, including tool continuation; restore the SAME
ID after interruption. No IDs are generated by the provider. Caller authorization,
cookies and custom transport cannot reach the service. No OAuth tokens enter the
Worker. Native Pi Responses streaming is used with retries/fallback disabled.
The actual `Assistant` installs the provider only with `ENABLE_MODEL_RUNNER=true`
and valid endpoint/key configuration. Existing deployment settings keep it off.

HMAC binds method, exact path, timestamp, round ID and exact UTF-8 body SHA256,
with 30-second freshness and redirects rejected. Authentication precedes credential
access. An fsynced round-ID/body-hash reservation precedes refresh/inference.
Duplicates/conflicts permanently fail; no prompt/output is journaled. Never prune
or roll back the journal. Its capacity is 10,000 rounds; arrange a safe successor
before capacity exhaustion without replaying old IDs. One registration/process
owns the live journal and credential session.

Only Sol/Luna and the documented stateless SIWC Responses subset are accepted.
Full input/history is preserved; function/custom tools become `additional_tools`.
Unsupported tuning/state fields are omitted, system messages/hosted tools rejected.
Tools execute in the caller; the service never starts follow-up rounds itself.
Availability still belongs to the selected registration/account policy.

SSE streams with backpressure, a 120-second deadline, 4 MiB total and 128 KiB frame
limits. Headerless and mixed-case SSE are accepted; valid framing/JSON and a
completed `response.completed` are required. Failed/incomplete/dropped streams
fail the round. Stop/disconnect abort inference, including late response bodies.
Fixed provider error codes expose no upstream response text and prevent automatic
harness replay of ambiguous work.

`openSiwcOwner` acquires its exclusive process lock BEFORE reading credentials.
Concurrent requests share one refresh. Refresh uses the issued client ID and
resource, never dynamic registration/API-key fallback. Replacement ID-token
identity/scopes are validated, then credentials are atomically written and file/
directory-fsynced before access is published. The durable `.refreshing` marker
precedes token dispatch and is cleared only after durable replacement. Any uncertain
result, timeout or persistence failure leaves it locked across restart. A round
cancellation does not abort a refresh already started: the sole owner finishes
rotation/storage under its own 30-second deadline. Never clear a marker or stale
owner lock blindly; stop all owners, inspect state privately, and explicitly
reauthorize the selected registration when rotation is uncertain. Protected
credential/config/key files are 0600 in owner-controlled 0700 directories with no
symlink paths; live files stay outside the checkout and deployment rollback.

## Durable Worker orchestration wiring

This code integration is implemented, not an activation TODO. A version/source-
checked postinstall patch at Pi 1.1.0's generation request boundary carries the
already-committed task and conversation IDs as internal model options. It applies
only to the explicit runner provider. It fails installation on incompatible Pi
versions/source rather than silently losing identity. Extension hooks are not
used as a security boundary because this SDK swallows their errors.

The Worker hashes its durable-object ID, conversation ID and generation task ID
into the runner round ID, then transactionally reserves a body hash before signed
network dispatch. Pi retry/recovery retains the task ID; tool continuation and
new submissions create successor tasks. Consequently retries/restarts cannot
mint a replacement round ID or redispatch an ambiguous round. Changed recovered
bodies conflict and fail closed. Cancellation during reservation may retain the
conservative fence but cannot fetch after Stop. A later intentional submission
has a new task ID. The existing admission journal still owns input deduplication
and cancellation epochs; historical messages are not rewritten. Child delegation
conversations remain distinct and use the runner's Luna model. Internal identity
headers never cross the transport boundary.

A Worker restart after reserving but before sending conservatively fails the
round rather than trying to infer whether the provider accepted it. Lost-result
recovery/retrieval is not implemented; this is explicit at-most-once dispatch,
not guaranteed completion. Never delete Worker `runner-round:v1:` reservations
or reset either dispatch fence during deployment/rollback.

2. Approve the selected registration, exact protected Spark credential provisioning,

   does not authorize copying its session or refreshing it on both hosts.
3. Approve a dedicated transport key, secure Worker/Spark provisioning, and exact
   TLS/private gateway, DNS/firewall/tunnel arrangement. None exists from this work.
4. Provision protected external files/directories and review this config schema
   (placeholders only; no actual config installed):

   ```json
   {
     "eligibility": "confirmed-for-this-deployment",
     "port": 4320,
     "identity": {"clientId": "<issued-client>", "subject": "<validated-subject>", "hostId": "urn:uuid:<distinct-vm-uuid>"},
     "credentialPath": "/<protected-runtime>/credentials.json",
     "transportKeyPath": "/<protected-runtime>/transport-key.hex",
     "stateDirectory": "/<protected-state>"
   }
   ```

   The credential uses `LocalSiwcCredential` with optional `earliestRefreshAt`
   (epoch milliseconds). The transport file is 64 lowercase hex characters for a
   dedicated 32-byte key. Config/credential/key files and their parent directories
   must have modes 0600/0700 and service-user ownership. State directory is 0700.
   Import preserves the VM host ID and validated client/subject mapping.
5. Separately start the reviewed test service using
   `node --import tsx services/model-runner/live-server.ts /absolute/protected/config.json`.
   It binds **127.0.0.1 only**; this command has not been run with real config.
   Validate one bounded live text/tool roundtrip and Stop before continuing.
6. Approve/install persistent **model service** boot configuration. The persistent
   GitHub Actions runner is separate. Current fake user model unit is active but
   disabled at boot; lingering is off. Persistence needs an approved system unit
   for the service user, or approved enabled user unit plus linger. Preserve
   credentials/owner lock/journal paths across restarts. Never send credentials
   through GitHub Actions or reset the fence on deployment/rollback.
7. Activate the already-implemented Worker integration through the reviewed
   deployment configuration: `ENABLE_MODEL=true`, `ENABLE_MODEL_RUNNER=true`,
   `MODEL_RUNNER_ENDPOINT=https://<approved-host>/v1/responses`, with subscription
   setup/Grok off. Provision `MODEL_RUNNER_TRANSPORT_KEY` separately as a Worker
   secret; it is never embedded in generated config or passed through Actions.
   The deployment generator/workflow support the flag and endpoint, disabled by
   default; staging's workspace-only target forces the runner off. New chats use
   runner Sol and delegates use runner Luna. Existing chats retain their saved
   provider selection and transcripts; create a new chat for the activated runner.
8. Validate real Worker/Spark TLS/auth, recovery, access revocation, model access

## Recoverable validation evidence

Tests use synthetic tokens/keys, temporary protected files, injected provider/
token transports and loopback HTTP only. Coverage includes HMAC tampering/skew,
native Pi streaming/tool continuation, headerless/fragmented SSE, terminal errors,
permanent fencing, cancellation during fsync/credentials/headers/stream, shared
refresh, atomic rotation, identity/scope checks, deadlines and restart locks.

An initial test caught concurrent access rejecting instead of joining refresh.
Independent review also found credential reads before locking, cancellation after
journal fsync and raw malformed-JSON startup errors. All were fixed with regression
coverage. Initial Mac log: `/tmp/pi-siwc-owner-test.log`; corrected owner log:
`/tmp/pi-siwc-owner-test-fixed.log`; full suite: `/tmp/pi-siwc-full-test.log`;
final contract log: `/tmp/pi-siwc-final-contract.log`. Logs are synthetic only.

Worker wiring follow-up validation adds actual pinned Harness recovery/retry,
changed-body conflict, sibling delegation and cancellation-during-transaction
regressions. The full authenticated `Assistant` runs in workerd/SQLite, signs real
HTTP requests to the loopback runner, completes tool continuation, survives process
reconstruction without duplicate dispatch, rejects tampered bodies, and propagates
Stop to the backend AbortSignal. Test-only allowlisting maps the exact HTTPS fixture
endpoint to native HTTP loopback; no public endpoint/TLS or real credential is used.

These full-runtime tests caught Workers rejecting `redirect:"error"` and requiring
bound global fetch; transport now uses manual mode with explicit redirect rejection
and Assistant supplies a bound fetch closure. An outboundService test adapter lost
body cancellation, so the final test uses native workerd sockets and explicit
reader cancellation. Initial recoverable logs are `/tmp/pi-cloudflare-native-diagnostic.log`
and `/tmp/pi-cloudflare-runner-stop.log`; passing native transport evidence is
`/tmp/pi-cloudflare-native-transport.log`. Initial Harness fixture configuration and
shared mutable policy fixture errors were corrected; no test failure is hidden by
skipping or weakening duplicate/cancellation assertions.

No new real-model test was run. Prior bounded Mac SIWC diagnostic results remain in
`services/model-runner/LIVE-RESULTS.md`; their one-shot fences/budgets were already
consumed. This implementation does not reuse them, inspect/copy their credentials,
refresh a session, or claim new real-model/production evidence. Hosted eligibility
is an activation prerequisite, not an implementation blocker.
