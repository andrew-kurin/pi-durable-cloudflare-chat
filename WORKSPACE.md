# Disposable project workspace V1

This feature is disabled by default and has not been deployed. The existing production configuration, model/auth loop, domain and deployment workflow are unchanged. Sol stays in Pi Durable; a separate task-scoped `TaskWorkspace` Durable Object owns the guest and its lifecycle. The guest contains Node, Git, Python and normal build utilities, with no second model, application credentials, GitHub write/deployment tokens or mounted production state.

The owner can explicitly open a disposable workspace for the configured trusted public `WORKSPACE_REPOSITORY` (`owner/repository`). When tools are enabled, `workspace_read`, `workspace_edit` and `workspace_exec` also activate it automatically when safe. The app admits one active owner workspace across conversations. It clones anonymously and saves the resolved initial commit as the immutable export base. Tools are registered only when the feature, namespace, project and image are configured. They select only a workspace approved for the calling conversation:

| Tool | Behavior |
| --- | --- |
| `workspace_read` | Read a bounded UTF-8 project file. |
| `workspace_edit` | Replace exactly one matching occurrence, or create a new file with an empty old value. |
| `workspace_exec` | Start one serial argv command and return a durable run ID. A shell is explicit argv, such as `sh -c`. |
| `workspace_status` | Read recorded/live process state and deadlines immediately without restarting work. |
| `workspace_wait` | Observe one explicit workspace/run for 10–30 seconds (default 20), returning early on completion, failure or stop; never creates a guest or starts/replays work. |
| `workspace_logs` | Return the last 16 KiB of a recorded stdout/stderr stream. |
| `workspace_cancel` | Signal the process group, then stop the entire guest after bounded grace. |
| `workspace_export` | Save an immutable base-relative binary patch and available logs for owner review. |

Read/edit/new commands wait for the active command to finish. Export requires a quiet workspace. File adapters restrict relative paths and resolved paths to the project and exclude direct `.git` edits. This is intended for the owner's trusted project, not arbitrary hostile repositories. Internet access permits public cloning and package installation. V1 does not add an elaborate network policy layer. External publication, deployment or security-setting changes still require explicit owner approval; the guest has no write/deploy credentials. There are no previews, snapshots, automated PRs or parallel workspace agents.

## Automatic activation

`WorkspaceCoordinator` owns activation policy for all three workspace-dependent tools. It reuses a ready guest and joins an existing startup rather than cloning twice. The original tool operation runs only after setup is ready. The tool card displays **Starting workspace…**, then **Workspace ready. Running tool…**; setup failures report that no tool operation ran and require a later owner request or explicit open to retry. Status, logs, exports and artifact downloads never start a guest. `workspace_status` returns an ordinary `absent` state when no guest exists, plus structured `activation.mode`/`nextStep` guidance. A legacy or expired implicit closed state points to an omitted-ID read/edit/exec call rather than a manual open; the tool-level compatibility `canAutoReplace` follows that policy. Explicit targets and stop/setup-failure states remain distinct. The optional `runId` inspects an existing process only: `process.state` reports `none` or `not_found` without creating a process, and historical runs are not presented as live after closure.

A closed guest has no resumable filesystem. A tool that omits `workspaceId` may start a fresh clone after a legacy or naturally expired guest, including one with prior edits or commands. The old workspace identity, ownership, operation history and artifact reference are retained. The model result and inline card explicitly say **Old edits were not restored**; artifact contents are not claimed as verified. An explicit old workspace ID remains pinned and is refused rather than retargeted. Known cancellation, interrupted setup and failed initialization block the current request. A later admitted owner message permits replacement of that specific predecessor, preventing automatic startup loops within the same request. No patch restoration or command replay occurs.

Each automatically created successor stores one durable `workspace-predecessor:<newWorkspaceId>` reference before its mapping becomes current. Tool results and the conversation workspace lookup expose that reference. Existing owner-only artifact routes continue accepting old workspace IDs; references may point to unavailable or incomplete artifacts and do not certify their contents.

The coordinator durably binds each activating operation ID and input fingerprint to its first workspace before dispatch. Retries stay pinned to that identity even after a new workspace is opened; the guest journal decides whether to return a prior receipt or reject an interrupted operation. The coordinator never retries a dispatched command. Cancellation records a durable stop generation for the current guest; reservation and pre-dispatch checks prevent pending activation from undoing it, even across a later manual reopen. Cancelling an older guest cannot block a newer one. A newly admitted owner message also permits automatic activation for new work, without starting compute on submission itself. Admission captures the workspace stop epoch at HTTP arrival and journals it with the submission: messages queued before a newer Stop and retries of old submission IDs cannot clear it. The epoch is preserved when new work is admitted, so earlier activation callbacks still fail their cancellation checks. A stale ready guest associated with an unfinished Stop must be cleaned up before receiving new work; while cleanup is pending, the tool says to wait rather than replay. Manual opening remains available.

New additive Assistant keys are `workspace-activation-op:<session>:<operationId>` and `workspace-auto-stop:<session>`, plus `workspace-submission:<session>:<operationId>` admission deduplication and the predecessor reference above. Existing identity mappings, guest journals, quotas, owner authorization and external-change approvals remain in force. Startup sharing is local to the coordinator instance; after reconstruction the guest controller remains the authority for interrupted initialization rather than silently recloning.

See [model tool result contracts](docs/tool-contracts.md) for bounded text continuation, sanitized file errors and raw-byte log-retention metadata. Existing run IDs, operation fingerprints, cancellation and immutable artifacts keep their established semantics.

## Waiting for commands

Use `workspace_wait` with the workspace UUID and durable run ID returned by exec for a running command. One call waits up to 20 seconds by default, optionally 10–30 seconds, checking state internally about every two seconds. An invocation memo retains its deadline across tool recovery, and explicit IDs prevent retargeting if the conversation later gets a fresh guest. Missing/stale runs never create a guest or a process. Ordinary status and the UI's 15-second polling remain immediate.

The result distinguishes successful completion (exit 0), failure, interruption, stopping/closed state, unavailable status and `still_running`, with observed time, actual remaining task/command milliseconds and an explicit next step. Normal wait-budget exhaustion returns `still_running` with the last verified running snapshot and its observation time, without starting another status RPC after the deadline. A status RPC that cannot finish within the remaining budget returns `unavailable`; an already-expired recovered invocation has no new observation and also returns `unavailable` without an RPC. A timed-out wait is not completion of the owner's work: wait again, then continue requested dependent work (such as `npm test` after installation succeeds). Read logs for failures or useful output rather than repeatedly fetching empty streams. Cancellation aborts local waiting, and owner workspace cancellation/alarms remain independently admitted; no execution/lifecycle queue is held while sleeping. A status RPC already dispatched before timeout/abort may still finish under the existing controller bounds, including ordinary lifecycle enforcement. No event framework or automatic dependent command dispatch is added.

## Lifecycle and limits

Run IDs and operation fingerprints are saved before dispatch. Duplicate exec requests report the existing run; reconnect asks for status/logs. SDK recovery marks arbitrary execution/edit/export as unsafe rather than replaying it. A missing PID, changed boot ID, missing exit record or ambiguous dispatch becomes interrupted. The app never silently restarts a command or lost container. Start a new task or issue an explicit new command after reviewing available work.

| Configurable default | Rationale |
| --- | --- |
| Task deadline: 90 minutes | Enough time for a normal edit/build/test loop without an open-ended guest. |
| Command deadline: 30 minutes | Accommodates installs, builds and test suites; an individual command may request up to 120 minutes, capped by the task deadline. |
| Idle cleanup: 15 minutes | Allows reading results and deciding the next step. A running process is active even if its logs are quiet. Completion starts a fresh idle window. |
| Warning window: smaller of configured 5 minutes or 20% of allotted task/command time | Avoids warning immediately on a five-minute command; includes actual seconds remaining and allows explicit owner extensions. |
| Graceful cancellation: 10 seconds | Allows termination and final writes before whole-container shutdown. |
| Final artifact budget: 20 seconds | A failed or hung export cannot keep compute alive indefinitely. |
| Ordinary adapter operation: 30 seconds; setup: 5 minutes | Setup permits a realistic public clone without thrashing. |

Routine installs, builds and test suites should omit `limitMs` and retain the 30-minute command default. A 10–30-second `workspace_wait` budget only bounds observation; it does not shorten the command deadline. Choose a shorter command limit only for an explicit task requirement. A command killed at its deadline leaves cancelled tests unverified; extending a limit does not fix a separate assertion failure.

`WORKSPACE_LIMITS` accepts a JSON override of the `*Ms` fields in `DEFAULT_WORKSPACE_LIMITS`. Validated caps are six hours per task, two hours per command, one hour idle, 15 minutes warning, 30 seconds cancellation grace, 60 seconds artifact/adapter operations and ten minutes setup. The owner can explicitly add 30 minutes to either task or command; extension does not revive a stopping/closed task. Task and command limits are displayed separately. Alarms poll every 30 seconds, keep active guests alive and enforce deadlines independently of log output. Cancellation bypasses the app's long-running POST admission queue, including during setup.

The resource class is `standard-1` (1/2 vCPU, 4 GiB RAM, 8 GB disk), with an app-owned one-active-workspace admission limit and at most 100 commands per task. Guest logs have a file-size limit. Exports cap patch output at 512 KB and use bounded Durable Object storage chunks. Logs preserve only their tails. Artifacts are immutable per export ID and available through existing owner authentication and same-origin mutation checks. Cancellation saves available work best effort, then stops compute; missing/truncated logs, capture failures and uncertain stop confirmation are reported. A patch captured while a command is still stopping is explicitly marked. No Git commit or PR is created by export.

The panel disables Save patch & logs while a command is active and enables it after status confirms completion. A stale panel or direct export request is checked again inside the controller's serial queue. An active-command rejection occurs before reserving the export ID, so the panel can retain that ID and retry after completion. Collection still reserves its ID durably before it starts: failed, interrupted or timed-out collection is never replayed, and a successful retry returns the original immutable artifact.

## Configuration and future integration

The implementation uses the [Sandbox 1.0 app-owned container API](https://developers.cloudflare.com/sandbox/sdk/migrate/changes-in-1-0/) and [request-independent process records](https://developers.cloudflare.com/sandbox/commands/run-background-processes/), not SDK 0.x sessions. Each call supplies cwd explicitly. A constructor restores inactivity management and alarms for a still-running guest.

`wrangler.workspace.jsonc` is a separate opt-in configuration, validated by Wrangler 4.149.0. Its feature flag is false and project/image values are blank. The production generator does not adopt this configuration or enable the feature. Sandbox 1.0 requires digest-pinned managed-registry images; the older `max_instances` field is unsupported for Durable Object scheduling. The Dockerfile has been built and smoke-tested locally. Uploading its image, configuring the registry digest, provisioning the container app, setting the trusted project and enabling the feature require separate approval. No image has been uploaded and no paid resource provisioned.

## Deployment wiring (manual, after prerequisites and approval)

The manual workflow accepts `production` (default) or `staging`. Each uses only its own GitHub environment variables/secrets and requires main. Staging selects `src/workspace-smoke.ts`, a separate fixed-operation shell harness on `pi-private-chat-workspace-staging`, with only a fresh Workspaces namespace and `workspace-smoke-v1` migration. It does not import Assistant, the credential store or providers, and needs no encryption secret or subscription setup. It reuses the signed owner Access checks and secure response headers; arbitrary argv, workspace IDs and extensions are refused. Its provider/login/web flags remain off regardless of environment values. Production entrypoint, credential validation, origin, routing, Assistant migration and secrets remain unchanged.

Add these variables to the selected environment only after reviewing that target's resource/egress authorization:

| Variable | Required setting |
| --- | --- |
| `PROVISION_WORKSPACE` | `true` explicitly selects the existing workspace template, Workspaces binding, additive `workspace-v1` SQLite migration and container configuration. Default `false` creates none of these. Keep this true after provisioning, even when disabling the feature, to retain cleanup bindings and migration history. |
| `ENABLE_WORKSPACE` | Default `false`. Set `true` only after activation approval. Requires provisioning. |
| `WORKSPACE_REPOSITORY` | One approved trusted public `owner/repository`, without URL, credentials or branch suffix. |
| `WORKSPACE_IMAGE_REFERENCE` | `registry.cloudflare.com/<this-account-id>/<repository>@sha256:<registry-manifest-digest>`. Tags, other registries and other accounts fail closed. The generator names it `workspace` and supplies `WORKSPACE_IMAGE=workspace` to the app. |

Both targets also require their own `CLOUDFLARE_ACCOUNT_ID`, `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, exact `APP_ORIGIN`, and the two GitHub environment secrets `OWNER_EMAILS`/`CLOUDFLARE_API_TOKEN` through the existing private-config path. Do not paste secrets into chat or public variables. The workflow builds/uploads one image only when its explicit `build_workspace_image` manual input is true; otherwise it uses the already pinned reference. It does not buy/upgrade subscriptions, manage Access policies or attach routes. Image upload is a separate approved action; the local image ID is not the registry manifest digest. A named digest-pinned image source resolves through `ctx.container.images`.

For the proposed staging smoke window, the generated defaults are a 12-minute task, 10-minute command and one-minute idle/warning period, leaving cleanup margin inside 15 minutes. Do not extend staging deadlines. The operator must enforce the overall approved window, cancel and verify guest destruction, including when API/runtime recovery is ambiguous. Native Cloudflare execution, alarm delivery and stop confirmation still require verification; these are not proven hard billing caps. No model prompt is needed for the shell lifecycle smoke. Each opened task clones the approved public repository and enables outbound Internet for Git/package operations; there are no guest model/deployment tokens. This egress activation requires the same explicit approval as staging resources.

After native validation and reviewed activation, use the production environment with its existing owner authentication/data settings. To disable a provisioned workspace, retain `PROVISION_WORKSPACE=true`, repository and pinned image, set `ENABLE_WORKSPACE=false`, and deploy after cancelling/exporting any active task. The bundle marker includes workspace mode/image/repository so bindings refresh. A deployment does not itself replace an already-running guest or guarantee artifact recovery. Delete staging resources/image only after stop confirmation and rollback-reference review; never remove the production Assistant namespace or encryption key.
